# 测试指南

## 概述

本项目使用 **Vitest** 作为测试框架，配合 **React Testing Library** 进行组件测试。测试分为单元测试和集成测试两个层面。

## 测试框架配置

### 依赖包

- `vitest`: 快速的测试框架
- `@testing-library/react`: React组件测试工具
- `@testing-library/jest-dom`: DOM断言扩展
- `@testing-library/user-event`: 用户交互模拟
- `jsdom`: 浏览器环境模拟

### 配置文件

- `vitest.config.ts`: Vitest主配置
- `src/test/setup.ts`: 测试环境设置
- `src/test/utils/testHelpers.ts`: 测试工具函数

## 单元测试 vs 集成测试

### 单元测试（Unit Tests）

**定义**: 测试单个函数、方法或类的功能，完全隔离外部依赖。

**特点**:

- ✅ 执行速度快
- ✅ 易于定位问题
- ✅ 测试覆盖面精确
- ❌ 无法发现组件间交互问题

**示例场景**:

```typescript
// 测试工具函数
describe('HistoryManager', () => {
  it('应该能够添加新的历史记录', () => {
    const historyManager = new HistoryManager(5);
    historyManager.add(mockImageData, 'blur', { intensity: 5 });

    expect(historyManager.canUndo()).toBe(true);
    expect(historyManager.getHistoryItems()).toHaveLength(1);
  });
});

// 测试状态管理
describe('EditorStore', () => {
  it('应该能够设置活动工具', () => {
    const { setActiveTool } = useEditorStore.getState();
    setActiveTool('blur', { intensity: 5 });

    expect(useEditorStore.getState().activeTool).toBe('blur');
  });
});
```

### 集成测试（Integration Tests）

**定义**: 测试多个组件或模块之间的交互和协作。

**特点**:

- ✅ 验证真实的用户场景
- ✅ 发现组件间接口问题
- ✅ 测试数据流和状态同步
- ❌ 执行速度较慢
- ❌ 问题定位相对困难

**示例场景**:

```typescript
// 测试Hook与Store的集成
describe('useImageProcessing 集成测试', () => {
  it('应该完整执行图像处理流程', async () => {
    const { result } = renderHook(() => useImageProcessing())

    act(() => {
      result.current.processEdit('blur', { intensity: 5 })
    })

    // 验证多个状态的协调更新
    expect(mockUiStore.setLoading).toHaveBeenCalledWith(true)
    expect(mockWorker.postMessage).toHaveBeenCalledWith({
      type: 'image-process',
      payload: {
        imageData: mockImageStore.currentImage,
        action: 'blur',
        params: { intensity: 5 },
        isHistoryNavigation: false,
      },
    })
  })
})

// 测试组件交互
describe('Canvas 集成测试', () => {
  it('应该响应鼠标滚轮缩放', async () => {
    render(<Canvas />)
    const canvas = screen.getByRole('img', { name: /图像画布/i })

    fireEvent.wheel(canvas, { deltaY: -100 })

    expect(mockEditorStore.setZoom).toHaveBeenCalled()
  })
})
```

## 项目中的测试实践

### 1. 工具函数单元测试

**测试对象**: `src/utils/` 下的纯函数
**测试重点**:

- 输入输出的正确性
- 边界条件处理
- 错误处理

**示例**:

```typescript
// src/utils/__tests__/historyManager.test.ts
describe('HistoryManager 单元测试', () => {
  describe('添加历史记录', () => {
    it('应该限制历史记录的最大数量', () => {
      for (let i = 0; i < 6; i++) {
        historyManager.add(createMockImageData(), `operation-${i}`);
      }

      expect(historyManager.getHistoryItems()).toHaveLength(5);
      expect(historyManager.getHistoryItems()[0].operation).toBe('operation-1');
    });
  });
});
```

### 2. 状态管理单元测试

**测试对象**: `src/store/` 下的Zustand store
**测试重点**:

- 状态更新的正确性
- 方法调用的副作用
- 状态间的依赖关系

**示例**:

```typescript
// src/store/__tests__/editorStore.test.ts
describe('EditorStore 单元测试', () => {
  describe('视图控制', () => {
    it('应该限制缩放级别在有效范围内', () => {
      const { setZoom } = useEditorStore.getState();

      setZoom(-1);
      expect(useEditorStore.getState().zoom).toBe(0.01);

      setZoom(20);
      expect(useEditorStore.getState().zoom).toBe(10);
    });
  });
});
```

### 3. Hook集成测试

**测试对象**: `src/hooks/` 下的自定义Hook
**测试重点**:

- Hook与Store的交互
- 异步操作的处理
- 副作用的正确执行

**示例**:

```typescript
// src/hooks/__tests__/useImageProcessing.integration.test.ts
describe('useImageProcessing 集成测试', () => {
  it('应该正确处理Worker错误响应', async () => {
    const { result } = renderHook(() => useImageProcessing());

    const errorMessage = {
      data: {
        type: 'image-processed',
        payload: { success: false, error: '处理失败' },
      },
    };

    // 模拟Worker错误响应
    act(() => {
      const messageHandler = mockWorker.addEventListener.mock.calls.find(
        call => call[0] === 'message'
      )?.[1];
      messageHandler?.(errorMessage);
    });

    expect(mockImageStore.updateImage).not.toHaveBeenCalled();
    expect(mockUiStore.setLoading).toHaveBeenCalledWith(false);
  });
});
```

### 4. 组件集成测试

**测试对象**: `src/components/` 下的React组件
**测试重点**:

- 用户交互响应
- 状态变化的视觉反映
- 组件间的数据传递

**示例**:

```typescript
// src/components/__tests__/Canvas.integration.test.tsx
describe('Canvas 集成测试', () => {
  it('应该在图像变化时重新渲染Canvas', async () => {
    const { rerender } = render(<Canvas />)

    const newImageData = createMockImageData(300, 300)
    mockImageStore.currentImage = newImageData

    rerender(<Canvas />)

    await waitFor(() => {
      const canvas = screen.getByRole('img', { name: /图像画布/i })
      expect(canvas).toHaveAttribute('width', '300')
    })
  })
})
```

## 运行测试

### 基本命令

```bash
# 运行所有测试
pnpm test

# 运行测试并生成覆盖率报告
pnpm test:coverage

# 运行测试UI界面
pnpm test:ui

# 运行测试一次（CI模式）
pnpm test:run
```

### 测试文件命名规范

- 单元测试: `*.test.ts` 或 `*.test.tsx`
- 集成测试: `*.integration.test.ts` 或 `*.integration.test.tsx`
- 测试文件位置: 与被测试文件同目录的 `__tests__` 文件夹

### 测试覆盖率目标

- 单元测试覆盖率: ≥ 90%
- 集成测试覆盖率: ≥ 70%
- 关键业务逻辑: 100%

## 最佳实践

### 1. 测试命名

```typescript
// ✅ 好的命名
describe('HistoryManager', () => {
  describe('添加历史记录', () => {
    it('应该能够添加新的历史记录', () => {});
    it('应该限制历史记录的最大数量', () => {});
  });
});

// ❌ 不好的命名
describe('test', () => {
  it('works', () => {});
});
```

### 2. Mock使用

```typescript
// ✅ 合理使用Mock
vi.mock('../../store/imageStore');
const mockImageStore = {
  currentImage: createMockImageData(),
  updateImage: vi.fn(),
};

// ❌ 过度Mock
vi.mock('../../utils/imageUtils'); // 单元测试应该测试真实逻辑
```

### 3. 测试数据

```typescript
// ✅ 使用测试工具函数
const mockImageData = createMockImageData(100, 100, [255, 0, 0, 255]);

// ❌ 硬编码测试数据
const mockImageData = new ImageData(
  new Uint8ClampedArray([255, 0, 0, 255]),
  1,
  1
);
```

### 4. 异步测试

```typescript
// ✅ 正确处理异步
it('应该处理异步操作', async () => {
  await act(async () => {
    result.current.processEdit('blur');
  });

  await waitFor(() => {
    expect(mockStore.updateImage).toHaveBeenCalled();
  });
});
```

## 持续集成

测试应该在以下情况下自动运行：

- 代码提交前（pre-commit hook）
- Pull Request创建时
- 代码合并到主分支时

```json
// package.json
{
  "lint-staged": {
    "*.{ts,tsx}": ["eslint --fix", "prettier --write", "vitest related --run"]
  }
}
```

## 总结

- **单元测试**：专注于单个功能的正确性，快速且精确
- **集成测试**：验证组件协作，确保用户场景正常工作
- **平衡使用**：70%单元测试 + 30%集成测试的黄金比例
- **持续维护**：测试代码也是产品代码，需要重构和优化
